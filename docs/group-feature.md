# 群聊实现说明

## 功能与规则

- 用户填写群名建群，服务端生成数字群号；初始成员只有群主。
- 搜索群号后提交申请，群主同意或拒绝。申请人可以查看“我的入群申请”。不提供好友邀请、管理员、转让群主或禁言。
- 支持群列表、群详情、成员列表、文字消息、历史与离线同步、未读数、退群，以及群主改名、踢人和解散。
- 新成员只看入群后的消息；重新入群使用新的入群序号和成员代次，不补发退出期间的消息。本地已有旧历史保留。
- 退出或被踢后保留本地历史，但服务端拒绝后续发送、拉取、成员查询、ACK 和已读操作。
- 群主不能退出或被踢；可以解散群。解散后的本地记录保留，列表显示“群已解散”。

## 大小群与可靠性

200 人及以下为小群，超过 200 人为大群，没有 200 人的入群上限。

| 项目 | 小群 | 大群 |
| --- | --- | --- |
| 在线接收 | 服务端推送最多 20 条正文 | 服务端提示群最新序号，客户端分页拉取正文 |
| 离线恢复 | 按本地连续游标分页拉取 | 按本地连续游标分页拉取 |
| 重试依据 | 群最新序号大于个人 ACK 序号 | 群最新序号大于个人 ACK 序号 |
| 存储 | 每条消息一份正文、每名成员一份进度 | 每条消息一份正文、每名成员一份进度，不生成逐成员离线正文副本 |

后台每 2 秒检查当前网关的在线用户，重发未确认正文或拉取提示。推送入队不等于投递成功：只有客户端落盘后的 ACK 才推进服务端接收进度。离线用户的进度保存在 MySQL，登录后恢复。客户端每 10 秒同步群资料和最新序号，也可以手动刷新。

群人数变更和发送共用群行锁；每次投递读取当前成员人数，自动切换正文推送和提示拉取。客户端只在本地消息序号连续、状态保存成功后 ACK，乱序正文会触发补齐。两种机制共用连续群序号和成员代次，因此切换不重置进度。重复正文按群号和序号去重。

ACK 与已读分离。已读只在群页面可见且窗口激活时推进到本地已同步位置。未读统计从个人入群/已读边界之后计算，并排除自己发送的消息；序号差不会直接当作未读数。

## 服务端实现

群聊使用已有 `group_service`：认证后的 WebSocket 网关覆盖请求 actor，经 `GroupClient::Execute` 调用 `GroupServiceImpl::Execute`。群服务调用 `MySQLHandler` 完成存储操作。SQL、建表、事务、幂等与进度查询均在 handler 中，连接池由 connector 管理；数据库操作切换到 MySQL 第 0 个连接池执行器，同一事务使用同一连接。

这里采用 **MySQL 群消息日志作为群聊的权威正文存储**，没有继续使用旧群聊分支的 MongoDB、Redis、Kafka 多次独立提交。群关系、正文、群序号和请求结果在同一事务内提交，减少跨存储恢复窗口。单聊原有存储链路保持独立。这个实现选择与讨论中的跨存储任务复用不同，但提供同样的持久化、幂等与重试语义。

| 表 | 用途 |
| --- | --- |
| `im_groups` | 群号、群名、群主、人数、解散状态、最新序号 |
| `im_group_members` | 成员有效状态、入群边界、成员代次、ACK 和已读进度；退出记录保留 |
| `im_group_applications` | 申请及审核状态 |
| `im_group_messages` | 群消息正文；群号与序号主键；发送者与客户端消息 ID 唯一键 |
| `im_group_requests` | 操作请求和结果，按账号与客户端请求 ID 幂等重放 |

对外群号为与账号相同长度的 10 位数字，`im_group_numbers` 保存唯一映射，`im_group_number_cursor` 在事务内串行分配。启动时自动为现有 `im_groups` 补齐号码；内部 Snowflake ID 保持稳定，已有成员、会话和历史消息关联不变。协议 `Group.number` 用于展示和搜索，`Group.id` 用于业务操作；服务端仍兼容按旧内部 ID 搜索。

群内消息序号使用从 1 开始的连续整数。消息发送时间、消息 ID 和序号由服务端生成。成员变化、人数更新、审核和发送都在群锁保护下执行。事务使用 READ COMMITTED，避免等待群锁后仍用旧快照判断成员资格。重新入群增加 epoch，迟到的旧代次 ACK、已读和客户端拉取响应不会作用于新成员状态。

同一请求 ID、同一内容重试返回原结果；相同 ID 的不同内容拒绝。重复待审核申请返回成功，不另建一条申请；已处理申请不能改为另一结果。群主身份、群有效状态和成员身份在服务端检查。

服务端启动时创建新表，独立建表文件为服务端 `scripts/sql/group_chat.sql`。需要正常业务账号具备建表权限，或提前建表。运行验证使用独立临时 MariaDB，没有修改现有 `ape_auth` 数据库。没有自动导入旧 `groups` / `group_members` 数据。

旧 WebSocket 群接口 201～208 和旧消息接口中的群发送返回 `UPGRADE_REQUIRED`，避免绕过审核进入另一套群存储。已有 GroupService 新增 Execute RPC，新客户端通过网关调用这一接口。群投递循环由 GroupService 管理启动和关闭，不再由 main 启动独立模块。

群消息与 RPC 已统一到两端共享的 `groupchat.proto`，包含 `GroupService.Execute`，原 `group.proto` 及其生成文件已删除。gRPC 路径为 `/groupchat.GroupService/Execute`，服务端 RPC 调用方与服务实现需要使用同版生成文件。旧建群、直接入群、邀请等 11 个 RPC 已移除；旧群表的存储方法、实时分发和 Mongo 离线回退调用也已清理。新群聊通过独立的消息日志与成员进度恢复。

旧表仅为 `ape_auth.groups`、`ape_auth.group_members`。部署清理后的服务端后，可按 `scripts/sql/drop_legacy_groups.sql` 先删成员表再删群表；删除会移除旧表中的全部数据。当前 `im_groups`、`im_group_members` 及其他 `im_group_*` 表必须保留。正式数据库删除由用户手动执行，未自动迁移旧表数据。

## 客户端实现

`ClientSession` 管理 `GroupService` 和 `WcdbGroupDao`。群显示在联系人分组和会话列表，群消息使用现有聊天窗口的标题、历史和输入框。原“添加好友”页改为“添加联系人”，输入一次号码同时查询用户和群聊，分别展示结果；创建群和我的入群申请也在该页。联系人中的群条目和聊天标题的“资料”按钮打开群详情。

固定布局由 Qt Designer 表单维护：`src/ui/mainIM.ui` 定义统一聊天和添加联系人页面，`src/ui/groupPanel.ui` 定义独立群资料窗口及其成员、审核和我的申请页面。点击联系人的群条目或聊天标题的“资料”按钮弹出 `GroupPanel`，该窗口不嵌入 `mainIM`，保存自己的目标群 ID，打开资料不会切换主聊天会话。窗口中的“发消息”才打开对应会话。`GroupService` 保持独立的群协议和缓存，单聊与群聊使用不同的会话类型，允许账号和群号数值相同。

群主改名时，新名称会去除首尾空白；空名称、超过 256 UTF-8 字节、与当前名称相同均拒绝。提交改名前弹出二次确认，服务端也拒绝名称未变化的请求。退出和解散均弹出二次确认，默认取消；群主隐藏并禁用退出按钮，服务端继续执行 `OWNER_CANNOT_LEAVE` 校验。这里的“同名”指新名称与当前群名称相同，不限制不同群使用相同名称。

WCDB `group_cache` 按账号保存群资料、消息和待确认操作。消息先单独保存，再保存连续同步游标；全部成功才发送 ACK。重启时依据实际存在的消息重建连续游标，不直接信任旧游标。提交前保存操作 ID 和内容，超时或断线保留待确认请求，重新登录后以原 ID 确认；群消息列表显示尚未确认的发送内容。

资料、成员、申请列表分页完成后才发布结果。每页使用独立 requestId，忽略迟到的旧页响应；同步期间收到变更通知会追加刷新。失败保留旧缓存。

## 协议

两端共享 `proto/groupchat.proto`，外层仍为 `SdkWSReq` / `SdkWSResp`。

| WebSocket type | 数据 |
| --- | --- |
| 250 | `Command` / `Reply`：群操作、发送、拉取、ACK、已读 |
| 251 | `Notice`：资料刷新或新消息提示；小群可以包含正文 |

Operation：0 列表、1 建群、2 搜索、3 申请、4 待审核申请、5 审核、6 成员、7 改名、8 退群、9 踢人、10 解散、11 发送、12 拉取、13 ACK、14 已读、15 我的申请。

群消息不复用单聊的 106 ACK 和 209 离线完成通知。拉取每页最多 50 条，成员/申请列表每页最多 100 条。文字最多 64 KiB，群名最多 256 UTF-8 字节，申请说明最多 512 字节。

## 验证与运行

客户端：Release 编译，开启 `IM_CLIENT_BUILD_GROUP_TESTS` 后运行 `group-cache-test -platform offscreen`。覆盖账号隔离、重复落盘、中文内容、重启恢复、待确认请求与群页面初始化。

服务端：开启 `APE_GROUP_TESTS`，`scripts/run_group_tests.sh` 下载并解包测试数据库程序，在独立临时目录和端口 33079 上运行测试，结束时关闭临时进程。测试实际审批创建 201 人群，覆盖审核、权限、入群边界、重复请求、ACK/已读区分、重新入群、大小群转换、分页、并发序号、踢人与发送竞态、拒绝结果和解散。结构调整后还验证了 GroupClient → GroupService → MySQLHandler 的本机 gRPC 链路，以及服务持有的 worker 生命周期。

生产服务没有在本次任务中启动，没有执行正式库迁移，也没有使用真实账号做双客户端联调。

## 边界

- 在线变更通知通过当前进程连接管理器发送；多网关的资料变化由周期同步兜底。各网关只检查自身在线用户的待接收消息。
- 消息正文、申请和幂等结果尚无自动过期策略，需按实际业务另定保留和归档规则。
- 大群避免逐成员消息副本和离线任务，但仍向在线成员提示最新进度。未读查询会扫描未读范围；超大规模可再增加聚合计数与提示合并。
- 客户端目前保留该账号已下载的群消息并在内存展示；大量历史的按需加载和虚拟列表可后续优化。
