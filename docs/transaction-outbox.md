# 跨存储任务与恢复

MySQL、MongoDB、Redis 和 Kafka 不共享事务。本次以 MySQL 的持久化任务表为恢复依据，采用至少一次执行和幂等处理：外部操作成功而 MySQL 提交失败时，下一次任务重新执行外部操作，最终收敛，不依赖跨库回滚。

## 单聊发送

1. `MsgService` 生成消息 ID、序号和时间，在 MySQL 事务内锁定账号对、检查双向好友关系与删除水位，并写入发送任务。幂等键为发送者账号加 `clientMsgID`；相同 ID、相同内容返回原消息，内容冲突则拒绝。
2. 后台任务再次检查好友关系，将正文按 `serverMsgID` 幂等写入 MongoDB，初始 `committed=false`。随后在当前 MySQL 事务中更新双方会话、未读序号和任务 `stage=1`。失败留下的未提交正文不会出现在正常历史与离线查询中。
3. 下一阶段再次检查关系，发布正文、写入 Redis 实时正文缓存，再等待 Kafka 的 broker 确认。仅 broker 确认不会结束任务：消费者成功调用 PushService 后，还必须写入 MySQL 的 `dispatch_done`。缺少这一确认时任务每 5 秒重新投递。
4. 消费者按消息 ID 和持久化回执去重。接收方在线时尝试推送；离线时保留 Mongo 正文与未确认接收状态，登录后同步。客户端收到消息后提交 ACK，ACK 与用户已读状态分离。

请求最多等待约 8 秒。正文和会话提交完成返回发送成功；尚未完成则返回 `PENDING`，后台继续处理，并通过原 `clientMsgID` 通知发送者。发送成功表示服务端保存成功，不表示接收方已收到。客户端保留待确认状态；后续确认或历史同步可以恢复该消息，迟到的待处理响应不会覆盖已确认状态。

## 删除好友

1. 好友事务锁定账号对，删除双向关系与会话、清理未读序号、记录删除水位、取消旧的待执行发送任务，并插入清理任务。这些 MySQL 操作一起提交。
2. 事务提交后返回逻辑删除成功。历史读取及投递均检查关系和删除水位，因此无需等待物理清理完成才阻止旧消息访问。
3. 后台按删除水位清理旧发送任务的正文载荷，取得 MongoDB 旧消息 ID，先清理 Redis，再删除 MongoDB 正文。外部失败后任务自动重试。
4. 所有清理都限定 `seq <= 删除水位`，重新添加好友后产生的新消息不会被旧任务清理。客户端收到清理记录后同步删除 WCDB 和内存中的旧消息。

删除成功时，物理数据可能仍在等待清理；不能把响应理解成所有存储都已完成擦除。Redis 不再生成最大投递水位或离线 ZSET。实时消息缓存和升级前遗留的单条 ACK 元数据按消息 ID 清理。

## ACK 与消费进度

登录恢复以 MongoDB 为唯一候选分页来源，按收件人、单聊类型、发布和接收状态筛选，每批最多 50 条。每条下发前再检查 MySQL 好友关系、删除水位、发送任务阶段和持久化 ACK 回执。Mongo 查询异常不伪装成空结果。纯消息校验已迁到 `util/message_validation.h`，网关不依赖 RedisHandler。

已删除 Redis 离线 ZSET 的生产/查询/群扇出、旧群消费标记、最大投递水位和 ACK 延迟双删。旧 `PullMessageBySeqs`、`AddPendingOfflineAck` RPC 明确返回 UNIMPLEMENTED，未使用的客户端封装已删除。Redis 保留 token、在线状态及 Kafka 分发正文缓存；正文缓存设置 7 天 TTL，并在 ACK 清理任务中删除。升级前已有的 ZSET 不再读取或写入，已有 TTL 的键自然到期；不自动批量删除业务 Redis 数据。

离线同步仍使用 MySQL ACK 回执和一次性 60 秒批次等待：队列满/关闭、断线或超时停止连接，未确认消息供重登恢复。单聊 AckMsg 只原子提交回执和清理任务，不再运行同步 Redis/Mongo 双删。旧在线 ACK 超时扫描已移除，不能把过期标记当作接收依据。

RedisConnector 的 Lua 调用将脚本、KEYS 和 ARGV 作为一条 EVAL 命令的参数提交，响应数固定为一。逐次调用 request.push 会新增命令而不是追加参数，曾导致 ACK 后台更新投递水位时触发 Boost.Redis 响应容量断言，使整个进程退出；这一封装已修正。`APE_OFFLINE_LOGIN_TESTS` 的回归测试覆盖命令线格式、响应数、消息元数据读取和离线收件人校验。

单聊 ACK 在 MySQL 的同一事务中保存 `im_message_receipts` 和 ACK 任务，提交后网关才移除本批离线等待项。后台重试 MongoDB 已投递标记和 Redis 正文缓存清理。ACK 接口失败时网关有限重试，仍失败则关闭连接，让后续登录重放，不静默推进同步进度。

离线下发写队列满、关闭或写失败时会停止当前连接，不再静默丢弃并等待 ACK。每批 ACK 使用一次性 60 秒截止定时器，ACK 全部持久化后取消等待；超时或断线关闭会话并清空该连接的内存待确认项，不修改持久化回执。断线标志在清理开始时设置，防止关闭发生在 ACK 等待创建之前导致永久挂起。未确认消息在重新登录时恢复，已落盘但 ACK 未提交的重复消息由客户端去重。`offline_disconnect_test`（启用 `APE_OFFLINE_LOGIN_TESTS`）覆盖提前/等待中断线、提前/等待中 ACK、超时、队列溢出和关闭后的写入，无需外部数据库。

单聊按每条持久化回执去重，不根据最大投递序号跳过全部较小序号。不再维护 Redis 最大投递水位。

Kafka 禁用自动提交及自动 offset 存储。每个分区串行处理，处理成功后提交该消息的下一 offset；不同分区并行执行，失败在当前分区重试。积压队列按阈值暂停、恢复拉取。重平衡代次用于阻止旧任务继续提交进度。投递和提交仍可能重复，因此不能承诺端到端恰好一次。

## 表和后台任务

服务端启动时初始化表，独立建表文件为 `scripts/sql/outbox.sql`。本次没有执行 SQL 或数据库迁移。

| 字段 | 含义 |
| --- | --- |
| `operation` | 1 发送，2 删除好友后的清理，3 ACK 清理 |
| `state` | 0 待执行，1 已领取，2 完成，3 取消 |
| `stage` | 发送任务 0 未提交正文阶段，1 正文保存及会话事务已提交 |
| `dispatch_done` | 消费者已完成 PushService 调用并提交确认，不等于客户端 ACK |
| `lease_token`、`lease_until` | 领取凭证及 45 秒租约，阻止过期执行者覆盖新领取者 |
| `attempts`、`last_error` | 执行次数及最近错误 |
| `available_at` | 下一次允许领取的毫秒时间戳 |

`msg_service/outbox_worker.cpp` 中的 OutboxWorker 由 MsgService 持有，通过 StartOutbox/StopOutbox 管理生命周期，数据库操作仍在 MySQLHandler 中。两个后台协程使用 `FOR UPDATE SKIP LOCKED` 领取任务。失败按指数退避重试，最长间隔 60 秒；进程退出后未完成任务保留，重启后恢复。事务和账号对锁只串行化同一对好友，其他账号对仍可推进，但外部 I/O 期间持锁会延长同一账号对的等待。发送幂等记录目前不自动删除，好友删除会清除相关旧正文载荷；长期任务与回执保留策略需要按数据规模另行安排。

排查可读取：

```sql
SELECT id, operation, state, stage, dispatch_done, attempts,
       available_at, lease_until, last_error
FROM im_outbox
WHERE state IN (0, 1)
ORDER BY id;
```

任务本身自动重试；应先修复依赖故障。确需提前重试时，仅调整待执行任务的 `available_at`，不要手动重置完成、取消或正在执行的任务。

## 其他检查结果与边界

- MongoDB 查询异常不再伪装成空结果；离线同步失败返回错误，避免误报同步完成。正文增加唯一消息 ID 索引，并设置 majority 写关注、journal 和连接超时。
- 历史分页从好友删除水位之后开始，并检查发送任务提交阶段，避免旧数据占据第一页或未提交正文被读取。会话未读序号的唯一键避免任务重试重复计数。
- 好友通知仍是在线刷新提示，离线或通知遗漏通过登录同步、手动刷新恢复；关系事实以 MySQL 为准，不依赖通知可靠送达。
- 后续群聊采用独立 MySQL 消息日志与逐成员进度，不再使用旧群聊的 MongoDB、Redis 和 Kafka 分支；不复用这里的单聊任务表。详见 [群聊功能](group-feature.md)。
- 在线状态和群成员缓存仍属于可重建的派生数据，不提供跨存储原子性。

本次仅进行源码检查与客户端、服务端编译，没有启动程序、连接数据库或执行故障注入、双客户端联调。
