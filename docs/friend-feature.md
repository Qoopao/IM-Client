# 好友功能实现说明

本次实现账号查找、好友申请、收到/发出的申请列表、接受/拒绝、好友列表与详情、从好友详情发起文字单聊。后续群聊实现见 [群聊功能](group-feature.md)；备注编辑和黑名单不在本次范围。

## 客户端

“添加好友”入口现为“添加联系人”：同一输入框同时查询用户账号和 10 位群号，各自展示结果并执行好友申请或入群申请。创建群和查看我的入群申请位于该页；群与单聊共用聊天窗口，布局可在 `src/ui/mainIM.ui` 和 `src/ui/groupPanel.ui` 中通过 Qt Designer 编辑。

单聊已读提交以服务端会话快照为边界：只有会话存在时，才提交本地已落盘且序号不超过 `maxSeq` 的已确认消息，已达到服务端 `readSeq` 的位置不重复提交。会话列表同步完成后补交当前可见会话的已读，避免本地旧缓存或同步时序导致 `Invalid read position or missing conversation`。

- `main.cpp` 恢复 `ApplicationController` 启动，取消直接显示 mainIM 的预览入口。
- `ClientSession` 持有 RemoteFriendDao、WcdbFriendDao、FriendService 和 FriendController，登录成功后启动好友同步，关闭会话时取消请求并清理状态。
- `FriendModel` 定义用户、好友关系和申请数据，申请状态为 Pending、Accepted、Rejected。
- `RemoteFriendDao` 匹配 requestId 和响应类型，处理连接断开、12 秒超时，以及 type=230 刷新通知。
- `FriendService` 先加载当前账号缓存，再按每页 100 条依次拉取好友和申请；完整成功后才原子替换缓存并更新业务数据。分页失败保留旧缓存。同步期间收到通知会在成功后追加一次刷新。
- `friend_snapshots` 是按 owner 隔离的 WCDB 表。一行保存一次完整好友与申请快照（protobuf 的 Base64），避免多页请求失败后留下半份列表。
- `FriendController` 是界面调用入口；查询、发送申请和处理申请都有处理中状态，防止重复提交。操作失败只使用 qWarning 输出。
- 联系人搜索栏新增添加按钮和刷新按钮。添加页按账号查找用户，填写说明并发送申请；新的朋友显示收到和发出的申请，接收方可接受或拒绝待处理申请。好友条目显示真实列表，详情显示昵称、账号、备注，并提供发消息按钮。
- 联系人搜索仍只过滤已经同步到本地的列表。导航栏属性保持不变，好友/群聊分组保持整行点击展开、收起。

## 协议

`proto/friend.proto` 是两端共享协议，客户端只生成 protobuf C++ 文件，服务端还生成 gRPC 文件。外层仍使用 SdkWSReq / SdkWSResp。

| WebSocket type | 操作 |
| --- | --- |
| 220 | 按账号查询公开用户信息 |
| 221 | 发送好友申请 |
| 222 | 分页拉取好友 |
| 223 | 分页拉取收到和发出的申请 |
| 224 | 接受或拒绝申请 |
| 225 | 删除双方好友关系 |
| 230 | 好友数据变化通知，客户端重新拉取列表 |

好友通知不参与聊天消息 ACK，不复用 type=209 的离线聊天同步完成通知。页面和关系数据以数据库查询结果为准。

## 服务端

- 新增 `FriendServiceImpl` 和 `FriendClient`，复用现有回调式 gRPC、Asio 协程及服务注册发现机制。服务端口为 50057，RPC 为 Execute。
- 网关覆盖请求里的 actor 和 operation，以已认证连接的 account_ 和外层消息类型作为真实身份及操作类型。
- `MySQLHandler::ExecuteFriendCommand` 在 MySQL 连接池的第 0 个 worker 上执行异步 SQL。事务中的操作使用同一条连接；SQL 参数用 format_sql 转义。
- `friend_applications` 保存申请 ID、双方账号、说明、状态和时间；`friends` 保存双方各一条关系及独立备注；`friend_pairs` 的账号对主键用来串行化同一对账号的并发修改。
- 拒绝自己、不存在的账号、超过 512 字节的说明和已是好友的申请。同方向待处理申请重复提交会返回原申请；反向申请不会自动接受。
- 仅申请接收方可以处理。接受操作在一个事务内更新指定申请并插入双向关系；关系唯一键防止重复插入。重复同样的处理返回原结果，已处理申请不能改成另一种结果。
- 提交成功后，网关向相关在线账号发送 type=230。当前服务和网关在同一个进程，通知通过已有 WSSessionManager 转发；跨进程、多网关部署需要另接通知路由。
- 列表使用 ID 游标和本次列表最大 ID 分页。通知期间客户端会重拉；用户离线时，下次登录同步恢复状态。没有新增可靠通知队列或好友通知 ACK。
- `scripts/sql/friends.sql` 包含表定义。首次好友请求会执行 CREATE TABLE IF NOT EXISTS；已有环境可提前用该 SQL 建表。正常运行的数据库账号需要建表权限，或提前建好表。本次只编译，没有执行 SQL 或启动服务。
- CMake 的源文件 glob 增加 CONFIGURE_DEPENDS，确保新增服务及协议生成文件被纳入构建。

## 主流程

A 查询 B -> A 发送申请 -> 服务端持久化 -> A 收到操作结果、在线 B 收到刷新通知 -> B 拉取申请并接受 -> 事务提交双方关系 -> A/B 收到刷新通知并同步列表 -> 点击好友详情中的发消息，进入已有 ChatService 单聊。

服务端不可达、超时或通知遗漏时，保留已有缓存，通过刷新按钮或重新登录确认最终状态。发送结果未确认不等于服务端一定没有保存。

## 生成协议文件

客户端在项目根目录运行：

```powershell
& .\vcpkg_installed\x64-windows\tools\protobuf\protoc.exe --proto_path=proto --cpp_out=src/proto proto/friend.proto
```

服务端使用自身 vcpkg 中的 protoc 和 grpc_cpp_plugin 生成到 src/proto。两端生成器版本分别匹配各自运行库，不混用项目 tools/protoc 目录中的旧版本。

## 删除好友

联系人详情提供删除好友按钮。客户端经 FriendController、FriendService 发出 type=225 请求，处理中禁用删除按钮。服务端在账号对锁保护下删除双向关系、关闭待处理旧申请，并在 `friend_chat_deletions` 中为双方保存清理时间和消息序号分界。

删除好友事务同时删除双方 MySQL 会话、级联清理未读序号、保存删除水位，并写入 `im_outbox` 清理任务；这些操作一起提交或回滚。提交后返回逻辑删除成功，MongoDB 和 Redis 的物理清理由后台重试完成。后台先清理 Redis，再删除 MongoDB，且只处理删除水位及之前的消息，不会删除重新添加好友后的新消息。旧发送任务同时取消，后台清理其正文载荷，避免重试恢复旧数据。已处理的好友申请保留。详细流程见 [跨存储任务与恢复](transaction-outbox.md)。

`Reply.clearedConversations` 返回对当前账号生效的清理记录。删除方收到响应即清理 WCDB 和内存消息，双方在线时通过 type=230 刷新，离线一方下次登录同步后清理。客户端按服务端序号清理旧记录和未确认消息，并忽略迟到的旧消息；重新添加好友后的新消息不会被旧清理记录删除。清理记录同时保存在本地好友快照中。

会话页的“发起聊天”按钮及按输入账号打开会话的逻辑已删除，输入框只用于搜索现有会话；好友详情的“发消息”按钮保留。

单聊发送任务的接收、正文保存及投递阶段均检查双向好友关系和删除序号，并与删除操作共用账号对锁。在线推送、离线推送通过 `MySQLHandler::WithFriendMessage` 再次校验，并跳过已经持久化 ACK 的消息。非好友发送返回 `NOT_FRIEND`，不保存或投递消息。网关使用登录账号覆盖消息发送者；消息时间和序号由服务端生成。Kafka 中已经删除的数据仅剩消息 ID 时，消费端跳过该记录。
